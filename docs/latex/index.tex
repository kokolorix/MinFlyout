\chapter{Min\+Flyout }
\hypertarget{index}{}\label{index}\index{MinFlyout@{MinFlyout}}
A system-\/wide flyout above the {\bfseries{minimize}} button -\/ the counterpart to the Snap Layouts that Windows shows above the maximize button. Pure Win32/\+\+C++20, GDI rendering, no runtime dependencies and no third-\/party libraries. The flyout previews the monitors with their configured zones; the layouts live in a JSONC file in the user profile and can be tied to particular screens.\hypertarget{index_main_flow}{}\doxysection{\texorpdfstring{Flow}{Flow}}\label{index_main_flow}

\hypertarget{index_main_design}{}\doxysection{\texorpdfstring{Design decisions}{Design decisions}}\label{index_main_design}

\begin{DoxyItemize}
\item {\bfseries{No DLL injection, no CBT hooks.}} Nothing is loaded into a foreign process. Detection asks through {\ttfamily WM\+\_\+\+NCHITTEST} via {\ttfamily Send\+Message\+Timeout} ({\ttfamily SMTO\+\_\+\+ABORTIFHUNG}), the documented interface Windows itself uses to evaluate the caption buttons, and otherwise reads public window data. See mfly::\+\+Probe\+Minimize\+Button.
\item {\bfseries{The button rect is measured, not guessed.}} Starting from the cursor, all four directions are searched for how far {\ttfamily HTMINBUTTON} still applies -\/ first coarsely in 4-\/pixel steps, then refined by binary search. This makes detection independent of theme, DPI and border width.
\item {\bfseries{And where nobody answers, it is computed.}} An app with its own title bar may report its button area as plain client space; then the position is derived instead, from the caption button block DWM reports, from the title bar strip, or in the end from the visible frame and the caption height. The arithmetic is in Caption\+Geometry.\+h, the ladder in mfly::\+\+Probe\+Source.
\item {\bfseries{Hooks in a dedicated thread.}} Low-\/level hooks are processed synchronously in the input path; if the same thread queried a hung window, the mouse would stutter system-\/wide. See mfly::\+\+Hook\+Thread.
\item {\bfseries{The flyout never activates itself}} ({\ttfamily WS\+\_\+\+EX\+\_\+\+NOACTIVATE} and {\ttfamily MA\+\_\+\+NOACTIVATE}), the target window keeps the focus.
\item {\bfseries{Flush edges.}} When the size is applied, the invisible shadow border from {\ttfamily DWMWA\+\_\+\+EXTENDED\+\_\+\+FRAME\+\_\+\+BOUNDS} is subtracted, otherwise a gap opens up between two windows placed side by side (mfly::\+\+Apply\+Zone).
\item {\bfseries{Windows announces the drag.}} {\ttfamily EVENT\+\_\+\+SYSTEM\+\_\+\+MOVESIZESTART} and {\ttfamily }...\+\_\+\+MOVESIZEEND bracket the modal loop {\ttfamily Def\+Window\+Proc} runs while a window is dragged. Registered {\ttfamily WINEVENT\+\_\+\+OUTOFCONTEXT}, the callback arrives on our own message loop -\/ the same promise the detection makes, and cheaper than guessing a drag from mouse movements (mfly::\+\+Drag\+Watcher).
\item {\bfseries{The touch overlay never takes input.}} {\ttfamily WS\+\_\+\+EX\+\_\+\+TRANSPARENT} plus {\ttfamily WS\+\_\+\+EX\+\_\+\+NOACTIVATE:} every touch point passes straight through to the window being dragged, and where the finger is comes from the mouse hook that already exists. Nothing the overlay does can interrupt the drag it is drawn for (mfly::\+\+Zone\+Overlay).
\item {\bfseries{Move is told from resize by the press, not by the event.}} {\ttfamily MOVESIZESTART} brackets both, so the hit test has to happen at the moment of the press -\/ before the window disappears into its loop and stops answering (mfly::\+\+App\+Controller::\+\+Remember\+Press). The answer is read as a blacklist rather than as a whitelist: asking for {\ttfamily HTCAPTION} looks equivalent and excludes every application that draws its own title bar, because such a window reports {\ttfamily HTCLIENT} there and moves itself. The sizing codes are the closed list (mfly::\+\+Is\+Sizing\+Hit\+Test).
\item {\bfseries{One arithmetic for both windows.}} Percent to pixels, the gap between tiles and the rule for overlapping zones live in Overlay\+Geometry.\+h, free of Windows dependencies and covered by {\ttfamily tests/\+\+Overlay\+Geometry\+Test.\+cpp}. The flyout\textquotesingle{}s miniature and the full-\/screen overlay therefore draw the same zone as the same rectangle.

A mfly::\+\+Layout is drawn as a miniature of the monitor, each of its mfly::\+\+Zone entries as a tile inside it. All four zone values are percentages of the monitor the miniature stands for. Values below 0 or beyond 100 reach onto the neighbouring screen (see \doxysectlink{page_config_config_zone}{The zone object}{1}).

Zones are meant to tile the screen without overlapping, the way the Windows snap layouts do -\/ but nothing enforces it. Where zones do overlap, the smallest one under the cursor wins, so a small tile drawn on top of a large one stays reachable.

A missing {\ttfamily layouts} section falls back to mfly::\+\+Default\+Layouts; an explicitly empty list hides the miniature area and leaves the text items.\hypertarget{index_main_capture}{}\doxysubsection{\texorpdfstring{Writing a zone down without counting pixels}{Writing a zone down without counting pixels}}\label{index_main_capture}
Guessing percentages is tedious, so {\bfseries{Ctrl+\+Alt+\+F11}} does it the other way round: arrange a window by hand and the line

mfly::\+\+Zone\+From\+Window is the exact inverse of mfly::\+\+Apply\+Zone: it measures the visible frame, the same rectangle {\ttfamily Apply\+Zone} positions, so the invisible shadow border cancels out and the pasted line reproduces the window it was taken from. mfly::\+\+App\+Controller::\+\+Capture\+Zone measures the foreground window and falls back to the one under the cursor where that is not measurable.\hypertarget{index_main_monitor_layouts}{}\doxysubsection{\texorpdfstring{Layouts for one screen}{Layouts for one screen}}\label{index_main_monitor_layouts}

Comparison ignores case and surrounding blanks, and the resolution accepts {\ttfamily x}, {\ttfamily X} and the multiplication sign, so a caption can be pasted straight out of the flyout. A screen that no layout applies to is left out of the flyout entirely -\/ which is also how a single screen can be excluded: give every layout an explicit list that omits it.

The rules live in Monitor\+Selector.\+h, free of Windows dependencies, and are covered by {\ttfamily tests/\+\+Selector\+Test.\+cpp}.\hypertarget{index_main_detection}{}\doxysubsection{\texorpdfstring{How the button is located}{How the button is located}}\label{index_main_detection}

Asking means {\ttfamily WM\+\_\+\+NCHITTEST} and, on {\ttfamily HTMINBUTTON}, the edge search: exact, because the window itself draws the answer. It runs first and unconditionally
\begin{DoxyItemize}
\item no assumption of ours stands in front of it, because an assumption that is wrong would hide a window that answers perfectly well. Computing needs nobody\textquotesingle{}s cooperation and walks three sources, from precise to approximate (mfly::\+\+Probe\+Source):
\end{DoxyItemize}
\begin{DoxyEnumerate}
\item {\ttfamily DWMWA\+\_\+\+CAPTION\+\_\+\+BUTTON\+\_\+\+BOUNDS} -\/ DWM reports the whole button block; it is divided into as many equal slots as the window styles call for.
\item {\ttfamily Get\+Title\+Bar\+Info} -\/ an API, not a message, so it also answers for a foreign process. It yields the exact title bar strip; only the button width is then derived from its height.
\item The visible frame plus the system caption height -\/ the last resort.
\end{DoxyEnumerate}

Which windows qualify is decided by the styles alone: {\ttfamily WS\+\_\+\+SYSMENU} and {\ttfamily WS\+\_\+\+MINIMIZEBOX} on a non-\/child window. {\ttfamily WS\+\_\+\+CAPTION} is deliberately not required -\/ an app that draws its own title bar usually drops it, and those are exactly the windows this path exists for (mfly::\+\+Caption\+Layout\+Of).

Which source produced a rectangle is written to the log on every detection. If none of them does, the log notes the window class and the {\ttfamily HT} code the window returned, so "{}it does not work with this app"{} becomes a line that says why (mfly::\+\+App\+Controller::\+\+Log\+Detection\+Miss).

The sibling message {\ttfamily WM\+\_\+\+GETTITLEBARINFOEX} would deliver the individual button rectangles in one go, but it carries a pointer into the receiving window\textquotesingle{}s address space and Windows is not documented to marshal it between processes. It is therefore deliberately not used.\hypertarget{index_main_diagnosis}{}\doxysubsection{\texorpdfstring{When a window stays undetected}{When a window stays undetected}}\label{index_main_diagnosis}
Point at the button that does not react and press {\bfseries{Ctrl+\+Alt+\+F12}}: mfly::\+\+Diagnose\+Window walks the whole chain for the window under the cursor -\/ ignore list, styles, frame, region, hit-\/test answer, {\ttfamily Get\+Title\+Bar\+Info}, the DWM block, the computed rectangle -\/ and ends with a verdict naming the step that failed. The report goes to the clipboard and to {\ttfamily minflyout-\/diagnosis.\+txt} next to the configuration.

It deliberately avoids the {\ttfamily WRITE\+\_\+\texorpdfstring{$\ast$}{*}\+\_\+\+LOG} macros: those are compiled out of a plain release build, and a diagnosis that only works in a debug build is no use when the problem appears in the release one. The report says on its second line which of the two builds is running, and carries mfly::\+\+Build\+Stamp so a stale EXE gives itself away.

The report prints two DPI values, and telling them apart explains a whole class of failures. {\ttfamily Get\+Dpi\+For\+Window} answers with the DPI a window {\itshape thinks} in -\/ its awareness context -\/ which for an application that is not per-\/monitor aware is 96 however large DWM actually draws it. Min\+Flyout is {\ttfamily Per\+Monitor\+V2} and reads physical coordinates, so everything it measures against the glass uses the screen\textquotesingle{}s DPI instead (mfly::\+\+Dpi\+For\+Window\+Monitor). Where the two lines differ, the window is one of those applications; where the caption arithmetic once used the wrong one, its region came out at a fraction of its proper size and the pre-\/filter rejected a cursor that was sitting right on the button.

{\ttfamily "{}trace\+Detection"{}}: {\ttfamily true} adds one line per gate of the detection, so a movement that never reaches the probe can be followed to the gate it died at.

Two things silence the detection with no error at all: Windows removes a low-\/level hook whose owner did not answer within {\ttfamily Low\+Level\+Hooks\+Timeout} -\/ which happens to any process sitting at a debugger breakpoint -\/ and the one-\/message-\/at-\/a-\/time throttle would stay armed forever if its message were lost. mfly::\+\+App\+Controller::\+\+Check\+Hook\+Alive watches for both and calls mfly::\+\+Hook\+Thread::\+\+Revive.

Watching the raw message traffic of a foreign window needs a hook inside that process -\/ that is what Spy++ does and what Min\+Flyout deliberately does not. Note that {\ttfamily spyxx.\+exe} only sees 32-\/bit processes; on an all-\/64-\/bit system it shows nothing at all and {\ttfamily spyxx\+\_\+amd64.\+exe} is the one to use.

If the file is malformed, the application keeps working with the default values and reports line and column of the error -\/ in the flyout as an item and on reload as a balloon on the tray icon.\hypertarget{index_main_flyout}{}\doxysection{\texorpdfstring{What the flyout shows}{What the flyout shows}}\label{index_main_flyout}
The upper part draws one row per monitor: a miniature for each layout that applies to that screen, in its aspect ratio, with the zones as tiles inside. Clicking a tile means "{}put the window on this monitor, into this zone"{} -\/ screen and position in a single click, because the hotspot carries its {\ttfamily HMONITOR} along (mfly::\+\+Apply\+Zone). Below the miniatures, separated by a line, come the text items from the providers.

With more than one row each carries a caption -\/ number, device name, resolution and, on the screen the window is on, {\itshape }(current). Those are exactly the selectors mfly::\+\+Selector\+Matches understands, so the configuration can be written from what the flyout shows.

A window without a sizing border cannot be tiled; for those the miniature area is omitted and only the text items appear. The same happens to a screen that no layout applies to -\/ it gets no row at all.

On a small panel the flyout comes out small -\/ correct in millimetres and awkward to hit. {\ttfamily "{}ui\+Scale"{}} multiplies the DPI it is laid out for, so fonts, paddings and miniatures grow together; \doxysectlink{page_config_config_uiscale}{Making the flyout bigger}{1} has the details and the rule that keeps an over-\/eager factor from pushing the flyout off the screen.\hypertarget{index_main_touch}{}\doxysection{\texorpdfstring{Dragging a window into a zone by finger}{Dragging a window into a zone by finger}}\label{index_main_touch}
The flyout is a menu: it is pointed at and clicked. The touch overlay is a target: it appears underneath a window that is already in motion and says where the window may be let go.

mfly::\+\+Zone\+Overlay draws two phases on one window: the trigger field configured by {\ttfamily touch.\+trigger}, and after {\ttfamily touch.\+dwell\+Ms} the zones of the touch layout across the whole monitor. It is layered, so DWM composites it and the window travelling underneath does not make it flicker; transparency is a color key plus one constant alpha rather than per-\/pixel alpha, which keeps ordinary {\ttfamily WM\+\_\+\+PAINT} drawing -\/ and with it the shared helpers in Painting.\+h -\/ working unchanged. GDI text writes no alpha channel, so per-\/pixel alpha would mean composing every label by hand.

The drop waits for the loop to end. A window still finishing its move loop would overwrite anything positioned during it, so {\ttfamily MOVESIZEEND} is the signal; where an application never sends one, a short grace after the finger lifts applies the zone anyway, and the poll timer withdraws an overlay whose drag was lost altogether.

Whether a press came from a finger is read from {\ttfamily MSLLHOOKSTRUCT::\+dw\+Extra\+Info}, which Windows stamps when it promotes a contact to a mouse message (mfly::\+\+From\+Pen\+Or\+Touch). Where that marker does not arrive, {\ttfamily "{}touch.\+also\+Mouse"{}} makes the route work for every drag regardless of what caused it -\/ which is also how the overlay is tried out on a machine without a touchscreen. \doxysectlink{page_config_config_touch}{The touch block}{1} lists the settings, \doxysectlink{page_config_config_ex_tablet}{A tablet that turns}{2} shows a tablet configured for both of its postures.\hypertarget{index_main_build}{}\doxysection{\texorpdfstring{Building}{Building}}\label{index_main_build}

Hold the mouse over the minimize button -\/ the flyout unfolds below it. Leaving it, clicking elsewhere or ESC closes it again; a click on the button itself minimizes as usual.

With a finger: drag a window by its title bar, rest it in the field that appears, and let go over one of the zones that unfold (\doxysectlink{index_main_touch}{Dragging a window into a zone by finger}{1}). Letting go anywhere else does nothing -\/ the drag stays an ordinary drag.

Two hotkeys work anywhere: {\bfseries{Ctrl+\+Alt+\+F11}} copies the zone of the active window as a configuration line (\doxysectlink{index_main_capture}{Writing a zone down without counting pixels}{2}), {\bfseries{Ctrl+\+Alt+\+F12}} writes the detection diagnosis for the window under the cursor (\doxysectlink{index_main_diagnosis}{When a window stays undetected}{2}).

A double click on the tray icon reloads the configuration -\/ that is the default action of the icon, and the menu marks the same command in bold. A right click opens the menu: {\itshape Paused}, {\itshape Restore all stashed windows}, {\itshape Open configuration}, {\itshape Reload configuration}, {\itshape Copy zone of the active window}, {\itshape Open diagnosis file} and {\itshape Exit}.\hypertarget{index_main_limits}{}\doxysection{\texorpdfstring{Limits}{Limits}}\label{index_main_limits}

\begin{DoxyItemize}
\item {\bfseries{UIPI:}} windows of processes with a higher integrity level do not answer {\ttfamily WM\+\_\+\+NCHITTEST}. For elevated windows Min\+Flyout itself has to run elevated.
\item {\bfseries{Custom title bars:}} a window that answers {\ttfamily WM\+\_\+\+NCHITTEST} with {\ttfamily HTMINBUTTON} is measured exactly; for one that does not, the position is computed. The computation assumes the system layout -\/ one block of equally wide buttons flush in the upper right corner -\/ so an app that puts its buttons somewhere else stays out of reach. {\ttfamily "{}button\+Detection"{}} selects which of the two ways is used, and a failed detection is written to the log with the class name and the {\ttfamily HT} code the window returned.
\item {\bfseries{Non-\/resizable windows}} (without {\ttfamily WS\+\_\+\+THICKFRAME}) show the size items greyed out, and cannot start a touch drag either.
\item {\bfseries{A window that is not per-\/monitor DPI aware rests on the estimate alone.}} All three of the precise answers fail together on such a window, and each for its own reason: it reports 96 dpi however large DWM draws it, it answers {\ttfamily WM\+\_\+\+NCHITTEST} over its caption buttons with {\ttfamily HTCAPTION} rather than {\ttfamily HTMINBUTTON}, and {\ttfamily DWMWA\+\_\+\+CAPTION\+\_\+\+BUTTON\+\_\+\+BOUNDS} comes back in a coordinate space that mixes the window\textquotesingle{}s own scale with the screen\textquotesingle{}s -\/ a well-\/formed rectangle sitting in the middle of the caption, which is what the flush-\/edge test in mfly::\+\+Caption\+Block\+From\+Dwm exists to catch. What carries these windows is the last rung of the ladder: the visible frame plus the screen\textquotesingle{}s title bar height. It holds up in practice, but it is a computation, so this is the class of window most likely to need a Ctrl+\+Alt+\+F12 report.
\item {\bfseries{The touch overlay stays on one screen.}} The trigger field follows the finger from monitor to monitor, but once the zones are unfolded they belong to the screen they opened on. Moving a window to another screen is what the flyout is for.
\item {\bfseries{Touch is told from mouse by a marker}}, not by a separate input path, so the distinction is only as good as {\ttfamily MSLLHOOKSTRUCT::\+dw\+Extra\+Info}. Where it does not arrive, {\ttfamily "{}touch.\+also\+Mouse"{}} makes the route work regardless.
\item {\bfseries{Stashed windows:}} mfly::\+\+Tray\+Stash restores them on exit and on {\ttfamily WM\+\_\+\+QUERYENDSESSION}; a crash of the host would leave them behind invisible.
