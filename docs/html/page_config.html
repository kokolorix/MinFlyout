Configuration reference

Every key MinFlyout understands, what it does, what it defaults to and what happens at the edges of its range. Examples follows with complete files for a small laptop, two screens of different shape, a tablet that turns, and a session spent chasing an app that stays undetected.

The mechanisms behind the settings are described on the main page: Writing a zone down without counting pixels writes a zone down without counting pixels, Layouts for one screen explains the monitor selectors, How the button is located what "buttonDetection" chooses between, and When a window stays undetected what to do when a window stays undetected.

The file

On first start %APPDATA%\MinFlyout\config.jsonc is created with a commented template - the same text mfly::ConfigStore::Reload writes, so the template and the defaults documented here cannot drift apart.

The format is JSONC, read by the parser in Json.h: line comments (//), block comments and trailing commas are allowed.

res/config.schema.json describes the whole file, so an editor can complete the keys, show these descriptions on hover and flag a typo such as showAllMonitor. In VS Code, either add an entry to json.schemas in the user settings - appending to the array rather than replacing it - with fileMatch set to &#42;&#42;&#47;MinFlyout/config.jsonc and url to the full path of res/config.schema.json; or put "$schema": "d:/Projects/MinFlyout/res/config.schema.json" as the first key of the file itself. MinFlyout ignores keys it does not know, so the file keeps working either way. Forward slashes are accepted in that path and save the escaping.

The trailing commas of the template stay flagged with a warning: the JSONC mode accepts them, but VS Code marks them anyway and offers no setting for that single diagnostic - the only switch is "json.validate.enable": false, which would also disable the schema.

Saving applies the changes. mfly::ConfigWatcher watches the folder, debounces for 300 ms and posts one message per save; a balloon on the tray icon confirms the reload. The tray menu entry Reload configuration does the same by hand, and "watchConfig": false turns the watching off.

Top-level keys

Key Type Default Meaning
hoverDelayMs integer, 0 - 5000 350 How long the pointer must rest on the minimize button before the flyout opens. 0 opens on the first movement over it, which makes crossing the title bar noisy. (mfly::Config::hoverDelayMs)
closeGraceMs integer, 0 - 5000 260 How long the flyout stays after the pointer has left it and the button. It survives the trip between the two regardless - a corridor spanning both is treated as inside. (mfly::Config::closeGraceMs)
showBuiltinItems boolean true Show the text items below the miniatures. false leaves the layouts alone. (mfly::Config::showBuiltinItems)
useWorkArea boolean true true bases every percentage on the work area, so a zone of 100 % height stops above the taskbar. false uses the full monitor area. Applies to the flyout, to the touch overlay and to what Ctrl+Alt+F11 measures, so the three always mean the same thing. (mfly::Config::useWorkArea)
showAllMonitors boolean true true draws one row per screen, so one click can move a window to another monitor. false shows only the screen the window is on. (mfly::Config::showAllMonitors)
uiScale number, 0.75 - 3 1.0 Size factor of the flyout, on top of the DPI scaling; the details are in Making the flyout bigger below. (mfly::Config::uiScale)
openHotkey string "Ctrl+Alt+Z" Opens the flyout for the foreground window from the keyboard; see Opening the flyout from the keyboard below. "" switches it off. (mfly::Config::openHotkey)
buttonDetection "auto", "hittest", "computed" "auto" How the minimize button is located; How the button is located walks the three. An unknown value is a configuration error and leaves the default in place. (mfly::Config::buttonDetection)
traceDetection boolean false One log line per gate of the detection, so a mouse movement that never reaches the probe can be followed to where it died. One line per change, not per movement, and only in a build with the logging macros compiled in. (mfly::Config::traceDetection)
logToFile boolean false Also write the log to %APPDATA%\MinFlyout\minflyout.log, UTF-8 with BOM, rotated to .log.1 at 1 MB. The debugger output is always written; this only adds the file, and only where logging is compiled in. (mfly::Config::logToFile)
watchConfig boolean true Reload as soon as the file is saved. Worth turning off if %APPDATA% is redirected to a share that reports no changes. (mfly::Config::watchConfig)
layouts array of The layout object five built-in The layouts the flyout offers. A missing key falls back to mfly::DefaultLayouts; an explicitly empty list [] hides the miniature area and leaves only the text items. (mfly::Config::layouts)
touch object see The touch block Dragging a window into a zone with the finger. (mfly::Config::touch)

Numbers outside their range are clamped rather than rejected: a hoverDelayMs of 100000 becomes 5000 and the file still loads. The only values that make the load fail are structural - a "layouts" that is not an array, a "buttonDetection" nobody knows, a malformed "touch". When the file does not parse says what happens then.

Making the flyout bigger

Windows sizes the flyout for the resolution of the screen, which on a small panel means small - correct in millimetres, and awkward to hit. "uiScale" multiplies that.

"uiScale": 1.4,

The factor is folded into the DPI the flyout is laid out for (mfly::ScaledDpi), and every metric already goes through that DPI. Fonts, paddings, corner radii and the miniatures therefore grow together and nothing can be pulled out of proportion - it is the same multiplication a higher-resolution screen would apply. Accepted range is mfly::kMinUiScale to mfly::kMaxUiScale; values below 1 shrink it.

A factor is a wish, not an instruction. On the very screen it is meant for it may ask for more room than there is, so mfly::FlyoutWindow::Show compares the measured size with the work area and walks the factor back until it fits - but never below 1.0, so asking for a larger flyout can never hand out a smaller one. A reduction is written to the log.

The touch overlay has no such setting: its trigger field and its zones are given in percent of the screen and are therefore already as large as the screen is.

Opening the flyout from the keyboard

"openHotkey" is the keyboard route to what the hover opens. Pressed, it opens the flyout for the foreground window, below its minimize button - the button is located the way the detection computes it when a window does not answer the hit test (mfly::ComputeMinimizeButton). A window without a minimize button gets the flyout below the middle of its title bar.

Such a flyout ignores where the pointer is. It closes on the same keys again, on Esc, on a click outside it, when a window is chosen in it, and when another window comes to the front. While detection is paused the hotkey does nothing.

The tray menu offers the same as Open flyout for the active window, with the hotkey shown beside it - reachable without a mouse through Win+B, the arrow keys and Enter, and the way out when the combination belongs to some other program. Opening the tray menu puts the taskbar in front, so the entry acts on the window that was in front before (mfly::AppController::UserWindow).

Inside the flyout, Tab and Shift+Tab move from monitor to monitor (the resize toolbar and the text items are stops as well), the arrow keys move within one, Home and End jump to its ends, Enter and Space choose. The details are at mfly::FlyoutWindow::HandleKey and mfly::HookThread::SetKeyNavigation.

Spelling (mfly::ParseHotkey): parts joined by '+', case and blanks do not matter.

Part Allowed
Modifiers Ctrl (Strg), Alt, Shift (Umschalt), Win
Keys A - Z, 0 - 9, F1 - F24, Space, Enter, Tab, Backspace, Insert, Delete, Home, End, PageUp, PageDown, Up, Down, Left, Right, Pause

A key other than F1 - F24 needs Ctrl, Alt or Win - "Shift+A" would swallow every capital A. Esc is refused, it is what closes the flyout. An unknown spelling is a configuration error. A combination that another program already holds is reported in a balloon after a reload and in the log; the tray menu entry keeps working.

On keyboard layouts with AltGr, Ctrl+Alt+letter is the same as AltGr+letter. Z carries no character on the German, Swiss or French layouts; on a layout where it does (Polish ż), pick another key.

The zone object

A mfly::Zone is a rectangle in percent of the reference area - the work area or the full monitor, depending on "useWorkArea".

Field Range Default Meaning
left -400 - 99 0 Left edge in percent.
top -400 - 99 0 Top edge in percent.
width 1 - 500 50 Width in percent.
height 1 - 500 100 Height in percent.

A zone does not have to stay on its monitor. A negative left or top, or a left + width (top + height) beyond 100, lets the window reach onto the neighbouring screen - { "left": -10, "top": 0, "width": 60, "height": 100 } starts a tenth of a screen width to the left of this monitor. The percentages always refer to the monitor the zone is picked on, so the overhang is measured in its width and height, not in those of the neighbour. At least 1 % of each axis has to stay on the zone's own monitor; a zone lying entirely beside it is dropped. Where there is no neighbouring screen, the overhanging part simply ends up off the desktop.

In the miniature such a tile is cut off at the edge and touches the frame there; the touch overlay likewise only shows the part on this screen. Windows assigns a window to the monitor holding the larger part of it - a per-monitor DPI aware application whose larger part lands on a screen with a different scale factor may therefore resize itself after being placed.

The limits are exactly the ones mfly::ZoneFromWindow applies to a measured zone (both go through mfly::LimitZone), so a line produced by Ctrl+Alt+F11 comes back out of the file as the window it was taken from - including a window hanging over the edge of its screen.

The touch trigger field (touch.trigger) is the one exception: it has to be reachable on this screen and stays within 0 - 99 / 1 - 100.

Zones are meant to tile the area without overlapping, the way the Windows snap layouts do - but nothing enforces it. Where they do overlap, the smallest one under the pointer wins (mfly::SmallestHit), so a small tile drawn on top of a large one stays reachable. Fractions are allowed and are how thirds are spelled: 33.33 / 33.34 / 66.66.

The layout object

Field Type Required Meaning
name string no Caption below the miniature, and the label in the touch trigger field.
zones array of The zone object yes The tiles, in drawing order. A layout without a single usable zone is dropped silently.
monitors selector or array of selectors no Which screens the layout is offered on; omitted means all of them. The accepted forms are listed in Layouts for one screen on the main page.

The touch block

Pick a window up by its title bar with the finger, rest it in the field that appears, and the zones unfold across the screen; let go over one of them and the window lands there. mfly::DragWatcher notices the drag, mfly::ZoneOverlay draws the target.

Key Type Default Meaning
enabled boolean true Whether the drag route is offered at all. (mfly::TouchConfig::enabled)
alsoMouse boolean false React to a window dragged with the mouse as well. Off by default - with a mouse the flyout is the shorter way - and the way to try the overlay out on a machine without a touchscreen. (mfly::TouchConfig::alsoMouse)
dwellMs integer, 0 - 5000 250 How long the finger must rest in the trigger field before the zones unfold. Too short and merely carrying a window across the middle of the screen opens them. (mfly::TouchConfig::dwellMs)
trigger The zone object 40 / 40 / 20 / 20 Where the field sits, in percent of the same reference area the zones use. It only exists while a window is actually being dragged, so it may be generous. (mfly::TouchConfig::trigger)
layouts array of The layout object the flyout's The zone sets offered while dragging. (mfly::TouchConfig::layouts)

Touch has its own layouts because it is a different task. Picking one of five miniatures with a mouse is a menu; doing it with a window already in mid-drag is not. So there is exactly one drop target: the first layout in touch.layouts whose "monitors" selector matches the screen the finger is on (mfly::LayoutsForMonitor). Leave layouts out entirely and the flyout's layouts are used instead, so a configuration that never heard of touch gains the drag route without being edited.

A screen no layout applies to simply shows no field there; the drag stays an ordinary drag, and moving to a screen that has one still works.

When the file does not parse

The application keeps running with the default values and reports line and column of the error - in the flyout as a clickable item, and on reload as a balloon on the tray icon (mfly::Config::error). Nothing is silently half applied: either a load succeeds and replaces the configuration, or the previous values stay in place.

Individual entries are more forgiving than the file as a whole. A layout without a usable zone, a zone that is not an object, a monitor selector that is neither a number nor a string - each is dropped and the rest is kept, because one malformed layout is not worth refusing a whole file over.

Examples

A small laptop screen

The flyout enlarged, and only the two arrangements that are comfortable on a 13-inch panel. Thirds are deliberately absent - they are cramped there.

{
"uiScale": 1.4,
"hoverDelayMs": 300,
"layouts": [
{
"name": "Halves",
"zones": [
{ "left": 0, "top": 0, "width": 50, "height": 100 },
{ "left": 50, "top": 0, "width": 50, "height": 100 },
],
},
{
"name": "Quarters",
"zones": [
{ "left": 0, "top": 0, "width": 50, "height": 50 },
{ "left": 50, "top": 0, "width": 50, "height": 50 },
{ "left": 0, "top": 50, "width": 50, "height": 50 },
{ "left": 50, "top": 50, "width": 50, "height": 50 },
],
},
],
}

An ultrawide next to a laptop

Thirds belong on the wide screen, halves on the laptop panel, and the full screen everywhere. Every layout names the screens it is offered on, so each row of the flyout carries only what makes sense there.

{
"showAllMonitors": true,
"layouts": [
{
"name": "Thirds",
"monitors": [ "3840x2160" ],
"zones": [
{ "left": 0, "top": 0, "width": 33.34, "height": 100 },
{ "left": 33.33, "top": 0, "width": 33.34, "height": 100 },
{ "left": 66.66, "top": 0, "width": 33.34, "height": 100 },
],
},
{
"name": "Wide + two",
"monitors": [ "3840x2160" ],
"zones": [
{ "left": 0, "top": 0, "width": 66, "height": 100 },
{ "left": 66, "top": 0, "width": 34, "height": 50 },
{ "left": 66, "top": 50, "width": 34, "height": 50 },
],
},
{
"name": "Halves",
"monitors": [ "secondary" ],
"zones": [
{ "left": 0, "top": 0, "width": 50, "height": 100 },
{ "left": 50, "top": 0, "width": 50, "height": 100 },
],
},
{
"name": "Full screen",
"zones": [
{ "left": 0, "top": 0, "width": 100, "height": 100 },
],
},
],
}

The selectors may be mixed in one list - [1, "secondary"] is valid - and a screen that no layout applies to is left out of the flyout entirely. That is also the way to exclude one: give every layout a list that omits it.

A tablet that turns

Rotating a Surface changes its resolution, so the resolution selector is also an orientation selector. Two touch layouts, one per posture: side by side when the screen is wide, stacked when it is tall.

{
"uiScale": 1.5,
"touch": {
"enabled": true,
"dwellMs": 250,
"trigger": { "left": 38, "top": 38, "width": 24, "height": 24 },
"layouts": [
{
"name": "Landscape",
"monitors": [ "2880x1920" ],
"zones": [
{ "left": 0, "top": 0, "width": 50, "height": 100 },
{ "left": 50, "top": 0, "width": 50, "height": 50 },
{ "left": 50, "top": 50, "width": 50, "height": 50 },
],
},
{
"name": "Portrait",
"monitors": [ "1920x2880" ],
"zones": [
{ "left": 0, "top": 0, "width": 100, "height": 50 },
{ "left": 0, "top": 50, "width": 100, "height": 50 },
],
},
],
},
}

The first matching layout is the one that shows, so the two lists must not both match the same screen - which is what the two resolutions guarantee.

Trying the touch route without a touchscreen

"alsoMouse" makes the overlay react to a window dragged with the mouse, so the whole route can be developed and watched at a desk. Everything else stays as it is.

{
"touch": {
"alsoMouse": true,
"dwellMs": 400,
},
}

A longer dwell helps here: a mouse crosses the middle of the screen faster and more often than a finger does.

Text items only

An explicitly empty layout list is a valid setting, and a different one from a missing key: it hides the miniature area instead of falling back to the built-in layouts. What remains is minimize, minimize to the notification area, always on top, minimize all windows of this app, minimize other windows and show desktop.

{
"layouts": [],
"touch": { "enabled": false },
}

Chasing an app that stays undetected

Nothing here changes what the flyout offers - it changes what MinFlyout says about itself. When a window stays undetected explains how to read the result.

{
// Log every gate of the detection, not just the successful ones.
"traceDetection": true,
// ... and keep it, so the log survives the next start.
"logToFile": true,
// Never ask the window, always compute - which shows whether the app
// answers WM_NCHITTEST at all or whether the geometry is what is wrong.
"buttonDetection": "computed",
}

Both log settings only take effect in a build with the logging macros compiled in (_DEBUG or _RELEASE_WITH_DEBUG_LOG). The Ctrl+Alt+F12 diagnosis works in a plain release build regardless, and says on its second line which of the two is running.
