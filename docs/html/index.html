MinFlyout

A system-wide flyout above the minimize button - the counterpart to the Snap Layouts that Windows shows above the maximize button. Pure Win32/C++20, GDI rendering, no runtime dependencies and no third-party libraries. The flyout previews the monitors with their configured zones; the layouts live in a JSONC file in the user profile and can be tied to particular screens.

Flow

[hook thread] [controller UI thread]
WH_MOUSE_LL ──PostMessage──▶ HandleMouseMove()
(does NOTHING but post) ├─ WindowFromPoint + GetAncestor(GA_ROOT)
├─ ask: WM_NCHITTEST == HTMINBUTTON
│ then edge search => button rect
│ (gated by nothing of ours)
├─ else, and only inside the caption button
│ region: compute from the DWM block, the
│ title bar strip or the frame
├─ hover delay ──▶ monitors + layouts + items
└─ FlyoutWindow::Show(content, buttonRect, dpi)

A finger has no hover and the minimize button is far too small for one, so touch takes a second route into the same mfly::ApplyZone. There the window itself is the pointer:

[WinEvent hook] [controller UI thread]
MOVESIZESTART ──PostMessage──▶ OnDragStart()
(a window is being moved) ├─ was the press a contact, on a caption?
├─ ZoneOverlay::ShowTrigger(monitor, layout)
├─ dwell in the field ──▶ SwitchToZones()
WH_MOUSE_LL ──PostMessage──▶ ├─ ZoneOverlay::Track(point)
MOVESIZEEND ──PostMessage──▶ └─ ApplyZone(window, zone, monitor)

Design decisions

  • No DLL injection, no CBT hooks. Nothing is loaded into a foreign process. Detection asks through WM_NCHITTEST via SendMessageTimeout (SMTO_ABORTIFHUNG), the documented interface Windows itself uses to evaluate the caption buttons, and otherwise reads public window data. See mfly::ProbeMinimizeButton.
  • The button rect is measured, not guessed. Starting from the cursor, all four directions are searched for how far HTMINBUTTON still applies - first coarsely in 4-pixel steps, then refined by binary search. This makes detection independent of theme, DPI and border width.
  • And where nobody answers, it is computed. An app with its own title bar may report its button area as plain client space; then the position is derived instead, from the caption button block DWM reports, from the title bar strip, or in the end from the visible frame and the caption height. The arithmetic is in CaptionGeometry.h, the ladder in mfly::ProbeSource.
  • Hooks in a dedicated thread. Low-level hooks are processed synchronously in the input path; if the same thread queried a hung window, the mouse would stutter system-wide. See mfly::HookThread.
  • The flyout never activates itself (WS_EX_NOACTIVATE and MA_NOACTIVATE), the target window keeps the focus.
  • Flush edges. When the size is applied, the invisible shadow border from DWMWA_EXTENDED_FRAME_BOUNDS is subtracted, otherwise a gap opens up between two windows placed side by side (mfly::ApplyZone).
  • Windows announces the drag. EVENT_SYSTEM_MOVESIZESTART and ..._MOVESIZEEND bracket the modal loop DefWindowProc runs while a window is dragged. Registered WINEVENT_OUTOFCONTEXT, the callback arrives on our own message loop - the same promise the detection makes, and cheaper than guessing a drag from mouse movements (mfly::DragWatcher).
  • The touch overlay never takes input. WS_EX_TRANSPARENT plus WS_EX_NOACTIVATE: every touch point passes straight through to the window being dragged, and where the finger is comes from the mouse hook that already exists. Nothing the overlay does can interrupt the drag it is drawn for (mfly::ZoneOverlay).
  • Move is told from resize by the press, not by the event. MOVESIZESTART brackets both, so the hit test has to happen at the moment of the press - before the window disappears into its loop and stops answering (mfly::AppController::RememberPress). The answer is read as a blacklist rather than as a whitelist: asking for HTCAPTION looks equivalent and excludes every application that draws its own title bar, because such a window reports HTCLIENT there and moves itself. The sizing codes are the closed list (mfly::IsSizingHitTest).
  • One arithmetic for both windows. Percent to pixels, the gap between tiles and the rule for overlapping zones live in OverlayGeometry.h, free of Windows dependencies and covered by tests/OverlayGeometryTest.cpp. The flyout's miniature and the full-screen overlay therefore draw the same zone as the same rectangle.

Configuration file

Configuration reference has every key with its default and its range, together with complete example files for a small laptop, two screens of different shape, a tablet that turns, and a session spent chasing an app that stays undetected. What follows here is the shape of the file.

On first start %APPDATA%\MinFlyout\config.jsonc is created with a commented template. The format is JSONC - comments and trailing commas are allowed:

{
"hoverDelayMs": 350, // hover delay before opening
"closeGraceMs": 260, // grace period before closing
"showBuiltinItems": true, // show the text items below the layouts
"useWorkArea": true, // compute percentages without the taskbar
"showAllMonitors": true, // offer every screen, not just the current one
"uiScale": 1.0, // size factor of the flyout (see page_config)
"openHotkey": "Ctrl+Alt+Z", // open the flyout for the active window
"buttonDetection": "auto", // ask the window, compute when it stays silent
"layouts": [
{
"name": "Halves",
"zones": [
{ "left": 0, "top": 0, "width": 50, "height": 100 },
{ "left": 50, "top": 0, "width": 50, "height": 100 },
],
},
{
"name": "Thirds",
"monitors": [ "3840x2160" ], // only on the wide screen
"zones": [ ... ], // as above
},
],
"touch": { // dragging a window into a zone by finger
"dwellMs": 250,
"trigger": { "left": 40, "top": 40, "width": 20, "height": 20 },
"layouts": [ ... ], // shaped like "layouts" above
},
}

A mfly::Layout is drawn as a miniature of the monitor, each of its mfly::Zone entries as a tile inside it. All four zone values are percentages of the monitor the miniature stands for. Values below 0 or beyond 100 reach onto the neighbouring screen (see The zone object).

Zones are meant to tile the screen without overlapping, the way the Windows snap layouts do - but nothing enforces it. Where zones do overlap, the smallest one under the cursor wins, so a small tile drawn on top of a large one stays reachable.

A missing layouts section falls back to mfly::DefaultLayouts; an explicitly empty list hides the miniature area and leaves the text items.

Writing a zone down without counting pixels

Guessing percentages is tedious, so Ctrl+Alt+F11 does it the other way round: arrange a window by hand and the line

{ "left": 2.03, "top": 65.74, "width": 96.15, "height": 28.7 },

lands on the clipboard, indented and with its trailing comma, ready to be pasted between two zones. The tray menu entry Copy zone of the active window does the same for the window that was in front when the menu opened - the way out when the hotkey belongs to something else.

mfly::ZoneFromWindow is the exact inverse of mfly::ApplyZone: it measures the visible frame, the same rectangle ApplyZone positions, so the invisible shadow border cancels out and the pasted line reproduces the window it was taken from. mfly::AppController::CaptureZone measures the foreground window and falls back to the one under the cursor where that is not measurable.

Layouts for one screen

Thirds are useful on an ultrawide panel and cramped on a laptop screen, so a layout can name the monitors it belongs on. Layout::monitors takes one selector or a list of them; without the key the layout shows up everywhere. mfly::SelectorMatches accepts:

Selector Matches
1, 2, ... the monitor number the flyout caption shows
"primary" the primary screen
"secondary" every screen that is not the primary one
"DISPLAY2" the device name; in full it needs JSON escaping: "\\\\.\\DISPLAY2"
"3840x2160" every screen with that resolution
"*" every screen - the default

Comparison ignores case and surrounding blanks, and the resolution accepts x, X and the multiplication sign, so a caption can be pasted straight out of the flyout. A screen that no layout applies to is left out of the flyout entirely - which is also how a single screen can be excluded: give every layout an explicit list that omits it.

The rules live in MonitorSelector.h, free of Windows dependencies, and are covered by tests/SelectorTest.cpp.

How the button is located

"buttonDetection" chooses between the two ways of finding the minimize button, and "auto" walks them in order:

Value Meaning
"auto" ask the window; compute the position when it stays silent
"hittest" only ask - a window with its own title bar is not detected
"computed" never ask, always compute

Asking means WM_NCHITTEST and, on HTMINBUTTON, the edge search: exact, because the window itself draws the answer. It runs first and unconditionally

  • no assumption of ours stands in front of it, because an assumption that is wrong would hide a window that answers perfectly well. Computing needs nobody's cooperation and walks three sources, from precise to approximate (mfly::ProbeSource):
  1. DWMWA_CAPTION_BUTTON_BOUNDS - DWM reports the whole button block; it is divided into as many equal slots as the window styles call for.
  2. GetTitleBarInfo - an API, not a message, so it also answers for a foreign process. It yields the exact title bar strip; only the button width is then derived from its height.
  3. The visible frame plus the system caption height - the last resort.

Which windows qualify is decided by the styles alone: WS_SYSMENU and WS_MINIMIZEBOX on a non-child window. WS_CAPTION is deliberately not required - an app that draws its own title bar usually drops it, and those are exactly the windows this path exists for (mfly::CaptionLayoutOf).

Which source produced a rectangle is written to the log on every detection. If none of them does, the log notes the window class and the HT code the window returned, so "it does not work with this app" becomes a line that says why (mfly::AppController::LogDetectionMiss).

The sibling message WM_GETTITLEBARINFOEX would deliver the individual button rectangles in one go, but it carries a pointer into the receiving window's address space and Windows is not documented to marshal it between processes. It is therefore deliberately not used.

When a window stays undetected

Point at the button that does not react and press Ctrl+Alt+F12: mfly::DiagnoseWindow walks the whole chain for the window under the cursor - ignore list, styles, frame, region, hit-test answer, GetTitleBarInfo, the DWM block, the computed rectangle - and ends with a verdict naming the step that failed. The report goes to the clipboard and to minflyout-diagnosis.txt next to the configuration.

It deliberately avoids the WRITE_*_LOG macros: those are compiled out of a plain release build, and a diagnosis that only works in a debug build is no use when the problem appears in the release one. The report says on its second line which of the two builds is running, and carries mfly::BuildStamp so a stale EXE gives itself away.

The report prints two DPI values, and telling them apart explains a whole class of failures. GetDpiForWindow answers with the DPI a window thinks in - its awareness context - which for an application that is not per-monitor aware is 96 however large DWM actually draws it. MinFlyout is PerMonitorV2 and reads physical coordinates, so everything it measures against the glass uses the screen's DPI instead (mfly::DpiForWindowMonitor). Where the two lines differ, the window is one of those applications; where the caption arithmetic once used the wrong one, its region came out at a fraction of its proper size and the pre-filter rejected a cursor that was sitting right on the button.

"traceDetection": true adds one line per gate of the detection, so a movement that never reaches the probe can be followed to the gate it died at.

Two things silence the detection with no error at all: Windows removes a low-level hook whose owner did not answer within LowLevelHooksTimeout - which happens to any process sitting at a debugger breakpoint - and the one-message-at-a-time throttle would stay armed forever if its message were lost. mfly::AppController::CheckHookAlive watches for both and calls mfly::HookThread::Revive.

Watching the raw message traffic of a foreign window needs a hook inside that process - that is what Spy++ does and what MinFlyout deliberately does not. Note that spyxx.exe only sees 32-bit processes; on an all-64-bit system it shows nothing at all and spyxx_amd64.exe is the one to use.

If the file is malformed, the application keeps working with the default values and reports line and column of the error - in the flyout as an item and on reload as a balloon on the tray icon.

What the flyout shows

The upper part draws one row per monitor: a miniature for each layout that applies to that screen, in its aspect ratio, with the zones as tiles inside. Clicking a tile means "put the window on this monitor, into this zone" - screen and position in a single click, because the hotspot carries its HMONITOR along (mfly::ApplyZone). Below the miniatures, separated by a line, come the text items from the providers.

With more than one row each carries a caption - number, device name, resolution and, on the screen the window is on, (current). Those are exactly the selectors mfly::SelectorMatches understands, so the configuration can be written from what the flyout shows.

A window without a sizing border cannot be tiled; for those the miniature area is omitted and only the text items appear. The same happens to a screen that no layout applies to - it gets no row at all.

On a small panel the flyout comes out small - correct in millimetres and awkward to hit. "uiScale" multiplies the DPI it is laid out for, so fonts, paddings and miniatures grow together; Making the flyout bigger has the details and the rule that keeps an over-eager factor from pushing the flyout off the screen.

Dragging a window into a zone by finger

The flyout is a menu: it is pointed at and clicked. The touch overlay is a target: it appears underneath a window that is already in motion and says where the window may be let go.

[None] ──window picked up by its caption──▶ [Watching] ──finger rests──▶ [Zones]
▲ (contact, resizable) │ │
└──────────────────────────────────────────────┴─────────────────────────┘
let go, ESC, or the move loop ended - a zone under the finger is applied

mfly::ZoneOverlay draws two phases on one window: the trigger field configured by touch.trigger, and after touch.dwellMs the zones of the touch layout across the whole monitor. It is layered, so DWM composites it and the window travelling underneath does not make it flicker; transparency is a color key plus one constant alpha rather than per-pixel alpha, which keeps ordinary WM_PAINT drawing - and with it the shared helpers in Painting.h - working unchanged. GDI text writes no alpha channel, so per-pixel alpha would mean composing every label by hand.

The drop waits for the loop to end. A window still finishing its move loop would overwrite anything positioned during it, so MOVESIZEEND is the signal; where an application never sends one, a short grace after the finger lifts applies the zone anyway, and the poll timer withdraws an overlay whose drag was lost altogether.

Whether a press came from a finger is read from MSLLHOOKSTRUCT::dwExtraInfo, which Windows stamps when it promotes a contact to a mouse message (mfly::FromPenOrTouch). Where that marker does not arrive, "touch.alsoMouse" makes the route work for every drag regardless of what caused it - which is also how the overlay is tried out on a machine without a touchscreen. The touch block lists the settings, A tablet that turns shows a tablet configured for both of its postures.

Building

  • Visual Studio 2022: open MinFlyout.sln, pick a configuration, F7. Projects: minflyout (EXE), json_tests (the unit tests for the JSONC parser, the monitor selectors and the caption geometry, run immediately after building) and docs (generates this documentation; not built automatically). Shared settings live in MinFlyout.props - in particular /utf-8, without which the UTF-8 literals are misinterpreted.
  • CMake: "cmake -S . -B build" and "cmake &ndash;build build"; "ctest &ndash;test-dir build" runs the unit tests, "cmake &ndash;build build &ndash;target docs" generates the documentation. Besides json_tests there is overlay_tests for the overlay arithmetic - a separate target because it carries its own main, and because the three sources json_tests names are not currently in the working tree.

Logging

WRITE_INFO_LOG(L"Flyout opened"); // message only
WRITE_DEBUG_LOG(L"Button probed", probeTime.ElapsedMs()); // + duration
WRITE_WARNING_LOG(L"Config rejected", config.error); // + detail

The macros in Log.h expand to mfly::log::Writer, which carries level, __FUNCTION__, __FILE__ and __LINE__. They are compiled in when _DEBUG or _RELEASE_WITH_DEBUG_LOG is defined; otherwise the arguments are discarded without being evaluated.

Output goes to OutputDebugStringW, and with "logToFile": true also to %APPDATA%\MinFlyout\minflyout.log. Every line is tab separated, has exactly eight columns and never leaves one empty - "-" stands in:

time thread level duration message function file(line) detail

Nothing is logged from the hook callbacks or from the cheap pre-test that runs on every throttled mouse move.

Reading the log in LogViewPlus

Parser DsvParser, file name pattern minflyout.log, "Is RegEx" off, and these parser arguments - the separators are real tab characters:

%d{yyyy-MM-dd HH:mm:ss.fff} %t %p %s{Duration} %m %c %s{Source} %S{Detail}

LogViewPlus derives the delimiter from the pattern itself: the first non-space character that is not part of a specifier, here the tab. The eight columns map as follows.

# Content Specifier Why
1 2026-08-19 22:14:07.913 %d{yyyy-MM-dd HH:mm:ss.fff} fff matches exactly three digits
2 thread id %t tells the UI thread and the hook thread apart
3 DEBUG INFO WARN ERROR %p the level names LogViewPlus knows
4 duration in ms, or - %s{Duration} own column, sortable
5 message %m may contain spaces
6 function %c mapped to the logger column, so filtering by origin works
7 AppController.cpp(193) %s{Source} no spaces, own column
8 detail, or - %S{Detail} window titles contain spaces

tools/minflyout-sample.log holds ten representative lines - one per level and one per overload - for the Testing tab, so the parser can be checked without running the program.

Application icon

Motif: the minimize stroke, with the unfolding flyout below it. The file res/minflyout.ico contains nine sizes from 16 to 256 px; the small ones are not downscaled but drawn separately (two instead of three menu rows, snapped to whole pixels). It is generated by tools/build_icon.py; res/icon.svg is the editable template of the large size. Everything is bound in via res/minflyout.rc, which also carries the version info.

Usage

Hold the mouse over the minimize button - the flyout unfolds below it. Leaving it, clicking elsewhere or ESC closes it again; a click on the button itself minimizes as usual.

With a finger: drag a window by its title bar, rest it in the field that appears, and let go over one of the zones that unfold (Dragging a window into a zone by finger). Letting go anywhere else does nothing - the drag stays an ordinary drag.

Two hotkeys work anywhere: Ctrl+Alt+F11 copies the zone of the active window as a configuration line (Writing a zone down without counting pixels), Ctrl+Alt+F12 writes the detection diagnosis for the window under the cursor (When a window stays undetected).

A double click on the tray icon reloads the configuration - that is the default action of the icon, and the menu marks the same command in bold. A right click opens the menu: Paused, Restore all stashed windows, Open configuration, Reload configuration, Copy zone of the active window, Open diagnosis file and Exit.

Limits

  • UIPI: windows of processes with a higher integrity level do not answer WM_NCHITTEST. For elevated windows MinFlyout itself has to run elevated.
  • Custom title bars: a window that answers WM_NCHITTEST with HTMINBUTTON is measured exactly; for one that does not, the position is computed. The computation assumes the system layout - one block of equally wide buttons flush in the upper right corner - so an app that puts its buttons somewhere else stays out of reach. "buttonDetection" selects which of the two ways is used, and a failed detection is written to the log with the class name and the HT code the window returned.
  • Non-resizable windows (without WS_THICKFRAME) show the size items greyed out, and cannot start a touch drag either.
  • A window that is not per-monitor DPI aware rests on the estimate alone. All three of the precise answers fail together on such a window, and each for its own reason: it reports 96 dpi however large DWM draws it, it answers WM_NCHITTEST over its caption buttons with HTCAPTION rather than HTMINBUTTON, and DWMWA_CAPTION_BUTTON_BOUNDS comes back in a coordinate space that mixes the window's own scale with the screen's - a well-formed rectangle sitting in the middle of the caption, which is what the flush-edge test in mfly::CaptionBlockFromDwm exists to catch. What carries these windows is the last rung of the ladder: the visible frame plus the screen's title bar height. It holds up in practice, but it is a computation, so this is the class of window most likely to need a Ctrl+Alt+F12 report.
  • The touch overlay stays on one screen. The trigger field follows the finger from monitor to monitor, but once the zones are unfolded they belong to the screen they opened on. Moving a window to another screen is what the flyout is for.
  • Touch is told from mouse by a marker, not by a separate input path, so the distinction is only as good as MSLLHOOKSTRUCT::dwExtraInfo. Where it does not arrive, "touch.alsoMouse" makes the route work regardless.
  • Stashed windows: mfly::TrayStash restores them on exit and on WM_QUERYENDSESSION; a crash of the host would leave them behind invisible.
